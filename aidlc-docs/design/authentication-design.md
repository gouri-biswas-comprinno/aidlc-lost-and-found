# Lost-and-Found JWT Authentication Design

## AI-DLC Stage

Elaboration: Solution Design

## Design Goal

Add simple JWT authentication to the existing React and Express application while preserving the existing reports API and MongoDB report data.

## Authentication Architecture

- React stores the JWT after a successful login and sends it in the `Authorization: Bearer <token>` header.
- Express provides signup, login, and logout routes.
- MongoDB stores users in a separate `users` collection through a Mongoose `User` model.
- Passwords are hashed before they are saved and are never returned in API responses.
- Express middleware verifies the JWT and rejects tokens found in the server-side blacklist.
- Logout adds the current token to a separate MongoDB blacklist collection and removes it from the React client.
- No sessions, refresh tokens, OAuth, roles, 2FA, OTP, or password reset flow are included.

## User Model

Collection: `users`

Fields:

- `name`: String, required, trimmed
- `email`: String, required, trimmed, unique, normalized for login
- `passwordHash`: String, required, securely hashed
- `createdAt`: Date, generated by Mongoose timestamps
- `updatedAt`: Date, generated by Mongoose timestamps

The API never returns `passwordHash`. The existing `reports` collection and `Report` model remain separate and unchanged.

## Authentication APIs

### Signup

`POST /api/auth/signup`

Body:

```json
{
  "name": "Example User",
  "email": "user@example.com",
  "password": "secure-password"
}
```

Behavior:

- Validate required fields and basic email/password rules.
- Reject an already registered email.
- Hash the password and create the user.
- Return `201` with safe user information, without the password hash.

Signup does not need to return a JWT; the user can log in after registration.

### Login

`POST /api/auth/login`

Body:

```json
{
  "email": "user@example.com",
  "password": "secure-password"
}
```

Behavior:

- Find the user by normalized email.
- Compare the supplied password with the stored hash.
- Return `401` for invalid credentials.
- Generate and return a JWT after successful verification.

Response shape:

```json
{
  "token": "<jwt>",
  "user": {
    "id": "<user-id>",
    "name": "Example User",
    "email": "user@example.com"
  }
}
```

### Logout

`POST /api/auth/logout`

Behavior:

- Require the current bearer token.
- Add the token to the server-side blacklist until its JWT expiration time.
- Return a successful response.
- React removes the token and current user from client state.

The blacklist uses a separate `blacklisted_tokens` collection with a small Mongoose model. Each record contains only `token` and `expiresAt`. Middleware checks the token and requires `expiresAt` to be later than the current time, so expired entries are no longer valid. A TTL index may remove expired records automatically. The collection remains separate from both `users` and `reports`.

## JWT Generation and Middleware

JWTs are signed after successful login with the configured secret and expiration. The payload contains only the user identifier and standard expiration data; it does not contain the password or unnecessary user details.

Authentication middleware:

1. Read the `Authorization` header.
2. Require the `Bearer` scheme and extract the token.
3. Reject the token if a non-expired matching blacklist record exists.
4. Verify the signature and expiration with the JWT secret.
5. Attach the user identifier to the request.
6. Continue to the controller or return `401`.

## Existing Report API Authentication

Keep read operations public so the current report discovery experience continues to work:

- `GET /api/reports`: public
- `GET /api/reports/:id`: public

Protect all report-changing operations with JWT middleware:

- `POST /api/reports`: authenticated
- `PUT /api/reports/:id`: authenticated
- `PATCH /api/reports/:id/resolve`: authenticated
- `DELETE /api/reports/:id`: authenticated

This adds authentication at the route boundary without changing the existing report document shape or destructive behavior. No ownership or role rules are added.

## React and Express Flow

1. React signup calls `POST /api/auth/signup`.
2. React login calls `POST /api/auth/login`.
3. React stores the returned token in client storage/state and keeps the safe user response.
4. The client request helper adds the bearer token to protected requests.
5. Express middleware validates the token before protected controllers run.
6. React logout calls `POST /api/auth/logout`, then removes its local token and user state.
7. Later requests with the logged-out token fail because the server blacklist rejects it.
8. Authentication failures are shown as ordinary client errors; the API does not expose stack traces or password data.

## Environment Configuration

Required server configuration:

- `JWT_SECRET`: private signing secret; required and kept outside source control.
- `JWT_EXPIRES_IN`: JWT lifetime such as `1h`; use a finite value so blacklist records can expire.

Existing configuration remains in use:

- `MONGODB_URI`: existing MongoDB connection string.
- `PORT`: existing Express port.
- `CLIENT_ORIGIN`: existing CORS origin where applicable.

The MongoDB blacklist needs no separate environment variable; its `expiresAt` value comes from the JWT expiration time. Do not create or modify `.env.example` during this design stage.

## Data Protection and Compatibility

- Authentication creates separate `users` and `blacklisted_tokens` collections; neither replaces or rewrites `reports`.
- No startup reset, collection drop, destructive migration, or report backfill is planned.
- Existing report fields, endpoints, and stored records remain intact.
- Route middleware is the only report behavior change: write operations require a valid JWT.
- MongoDB operations continue using the existing Mongoose models and structured queries.
